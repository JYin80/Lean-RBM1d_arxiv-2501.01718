# RBM1D 团队章程（Claude 团队，2026-09-25 起生效）

> 本文件由通用的《Claude 版 Lean 形式化协作方案》实例化而来，是 RBM1D 调度与监督的工作规则。
>
> **RBM1D 的具体约定**（与下文有出入时，以这里和 `CLAUDE.md` 为准）：
> - 模型：低级 = Sonnet（`prover` high，`prover-hard` xhigh）；高级 = Opus；最高级 = Fable（max）。决定见 `docs/DECISIONS.md`。
> - 执行中枢只执行 `docs/queue/CONTROL.md` 中 **Released tickets** 列出的工单，以及 **Approved instructions** 中的指令；对 CONTROL.md 只能追加 `done:` 行。
> - 状态文件取值：`claimed | proving | preflight-fail | built | auditing | audit-pass | audit-fail | blocked | merged`（见 `CLAUDE.md` §2）。
> - 执行中枢每轮更新 `docs/queue/HUB.alive`，作为在线信号；执行中枢用 Sonnet，`/loop 10m`。
> - 验收用 Opus 的 high（不用 xhigh），只看分支相对 main 的改动、目标声明和所用声明的签名，不通读依赖文件（见 `.claude/agents/auditor.md`）。
> - 总调度的空闲心跳从简：先看信箱文件的修改时间，没有变化就只排下一次心跳（§6）。
> - 工作树位置：`../RBM1D-wt/T####`，分支 `t/T####`。
> - 数学 gate 与完成合同：`docs/PLAN.md`；路线账本：`docs/ROUTES.md`。

## 0. 总体架构

| 位置 | 角色 | 能做什么 | 不做什么 |
| --- | --- | --- | --- |
| **Cowork 主会话** | 总调度 | 与用户确认目标；核查并拆解数学目标；写工单规格；预建接力链；处理异常；汇总验收结论；调用最高级模型子代理做数学强力论证；维护给用户看的清单与蓝图 | 不写 Lean；不在仓库执行任何 git 写操作 |
| **Cowork 定时任务** | 独立数学监督 | 由事件触发（另有每天一次兜底），每次开一个全新会话，只读核查**路线层面**的问题 | 不派单、不改文件（专用监督目录除外）、不放行验收；不重复逐单的数学核对 |
| **Claude Code 常驻会话（Mac）** | 执行中枢 | 从文件信箱领取工单；为每个工作组启动证明和验收子代理；按总调度指令合并已验收成果、跑全库构建 | 不做数学或路线判断；不改工单规格；不自行放宽条件 |
| **Claude Code 子代理（Mac）** | 执行团队 | 在各自的 git 工作树里先做数学预审，再写 Lean、构建、写报告；或做独立验收 | 只写本单指定的文件 |

**为什么要执行中枢。** Cowork 运行在云端，能读取你 Mac 上的仓库，但不能直接启动 Mac 上的 Claude Code 子代理，也不适合在那里编译 Lean：它的设备 shell 是一台 Linux 虚拟机，单条命令最长 3 分钟。执行中枢就是 Cowork 在 Mac 上的手。它本身不保存状态，全部状态都在仓库文件里，所以上下文被压缩或会话重启都不会丢东西。

**通信方式。**
- **主通道：仓库里的文件信箱**（§5）。总调度写工单和控制指令，执行中枢每 10 分钟轮询一次（Claude Code 的 `/loop 10m`），把状态和报告写回仓库，总调度在心跳时读取。
- **可选加速：会话间消息。** 如果终端会话开启 Remote Control 后，能出现在 Cowork 的可达会话列表里，总调度可以发一句「有新单」立即唤醒执行中枢。这条通道不是必需的，没有它也能运转。

## 1. 组织结构

- **1 名总调度（Cowork 主会话）**：使用用户指定的高级模型。与用户确认目标和证明口径；核查并拆解数学目标；写工单规格；划分文件所有权；处理异常；汇总验收结论；独占共享状态文件的修改（§5）。
- **1 名独立数学监督（Cowork 定时任务）**：使用用户指定的高级模型。常规检查用 high，发现疑点时升到 xhigh 或 max 复核。它由事件触发，不按固定钟点跑（见下）。每次都是全新会话、没有记忆，因而与总调度真正独立。它不占证明工作组名额。
- **1 个执行中枢（Claude Code 常驻会话）**：用低级模型（Sonnet），只做机械执行。它的上下文每次轮询都要重新过一遍，用高级模型空转最费额度。它只按工单和控制文件行事，遇到文件里没写清的情况就停下，写报告等待总调度。
- **执行团队（Claude Code 子代理）**：每组首轮由低级模型子代理先做数学预审，PASS 后直接写 Lean；然后由全新的高级模型子代理独立验收。子代理的模型、推理强度和可用工具固定在 `.claude/agents/` 的角色定义里（附录 A），不靠提示词约束。
- **1–3 名数学强力论证 agent（临时）**：总调度在 Cowork 里直接调用的最高级模型子代理。只做数学、只读仓库，交付完整论证后退出，不占常设岗位。
- **用户**：决定项目范围、论文忠实度、三个模型级别各自对应的具体模型；搭建本地文件夹和 GitHub 仓库；启动执行中枢；批准 Workflow 的使用和 Mac 上的权限白名单（附录 C）。

每张工单指定一名负责人和明确的可写文件范围；同一时间不让多个 agent 编辑同一个文件。

### 独立数学监督

**分工。** 逐张单的数学核对由预审和验收负责，监督不重复这项工作。监督只回答验收看不到的**路线层面**问题：
- 已派和在做的这些单串起来，能不能真正到达目标 gate；
- 是否一直在产出推广不了的特例：只对某个特例参数、只对首格、只对固定常数成立的结果反复出现；
- 某条路线已经花了多少单，和它的实际进展相比是否合理；
- 跨工单的接口和假设能否同时满足（量词、指数、尺度、非退化性），尤其是从局部或条件结论走向一般结论的那一步。

**触发方式：事件触发，另有每天一次兜底。** 监督是一个 Cowork 定时任务，平时每天只按计划跑一次兜底检查。下列事件一发生，总调度立即手动触发一次，并附上事件说明：
1. 任一工单预审 FAIL／BLOCKED，或验收 FAIL；
2. 同一个 gate 的证明单每累计 25 张；
3. 总调度提出新路线、更换路线，或准备做路线级决定（§4）。

项目空闲时不触发，也就不消耗。

**输入要收窄。** 总调度维护一页路线账本 `docs/ROUTES.md`，列出每个 gate 走哪条路线、已用多少证明单、是否闭合、未决问题和最近的失败。监督每次：
1. 先读这一页；
2. 再读自上次检查以来的新工单和失败报告；
3. 发现疑点时，才去打开具体的 Lean 陈述、它的生产者和论文原文。

不能只凭总调度或工人的摘要下结论，也不通读历史文件。

**路线预算。** 同一个 gate 累计约 50 张证明单仍未闭合，监督自动给出「建议 HOLD」，理由写「超出路线预算，需数学评审」。

**结论与通道。** 结论只有三种：**PASS**、**建议 HOLD**（路径不清，但新派单已暂停）、**建议 STOP**（路径不清，仍在派新单）。
- 结论写入唯一允许监督写的位置：`docs/supervisor/<日期时间>.md`。总调度下一次心跳（≤ 20 分钟）读取。
- HOLD／STOP 须附可核查的来源、准确的数学缺口、最早可见时间，以及其后派发的工单；不猜测缺失的证据。
- 监督不与用户对话。用户如希望 STOP 时直接收到提醒，可以给这个定时任务开推送通知，这是可选项。

**成本与自检。** 目标是每天 2–4 次、每次约 10–20 万 token，约占项目总消耗的 5%。每次结论都留在监督目录里。如果连续约 20 次检查都没有一次 HOLD/STOP 改变过决定，就进一步降低兜底频率或收紧触发条件。

**监督不做的事**：不派单，不改工单状态，不放行验收，不合并结果，不决定恢复派单。

**收到 HOLD／STOP 之后**：总调度在控制文件里写 `HOLD`，暂停新的 Lean 派单并进入自检，通常调用 1–3 名最高级模型子代理独立求解并协调其结论。确认数学路径确实闭合后，才改回 `RUN`。

### 工单队列与并行度

**并行单位是工作组，不是 agent 数量。** 一个「预审并证明 → 独立验收」接力链算 1 组，在执行中枢里就是一条 Workflow pipeline。
- 真实上限由 Mac 能同时跑几个 `lake build` 决定。Mathlib 类项目很吃内存，建议先实测，初始按 **3–4 组**。
- Workflow 默认建议少于 10 个 agent，多于这个规模需要用户在 Claude Code 设置里调高。
- 只有确有已完成起始数学核查、数学上互相独立且文件互斥的真实目标时，才开满并行。纯等待的验收不算生产性工作组。

**提前预建接力链**：总调度完成起始核查和文件分配后，一次写好该组的工单规格，写明证明和验收两个阶段以及放行条件。执行中枢据此启动 Workflow：证明阶段报告预审 PASS 且构建成功，才进入验收阶段。**预审未 PASS 前不得写 Lean。**

**及时补位**：一组的证明阶段完成后，可以启动另一组不依赖其验收结果的目标。未验收的证明不得作为新组的已证明输入。

**控制验收积压**：待验收队列上限默认 **10 张**，用户可调整。达到上限时，控制文件写 `AUDIT_FIRST`，执行中枢暂停放行新的首轮任务。

主机并发、模型额度或真实目标不足时，总调度记录具体限制，不制造填充工单。

## 2. 每个证明的基本流程

每个 Lean 证明都要经过以下三个环节。一个工单可以包含多个证明，但每个证明要有自己的预审结论和验收结论。

| 环节 | 在哪里 | 主要工作 | 通过条件 |
| --- | --- | --- | --- |
| **a. 数学预审** | `prover` 子代理，在本组工作树 | 核对数学陈述、假设、量词、依赖和证明路线；检查边界情形和假设能否同时满足 | 报告里先写明 PASS 和依据，才能进入 b；FAIL／BLOCKED 时停止写入并报告 |
| **b. Lean 书写** | 同一 `prover` 子代理 | 在指定文件中完成证明，编译相关模块，记录关键引理和遇到的问题 | 构建通过；不留 `sorry`；不靠未经批准的新增公理 |
| **c. 独立验收** | 全新的 `auditor` 子代理，在自己的工作树中检出证明分支 | 比对数学目标与 Lean 陈述；检查空真、隐藏假设、循环依赖、边界情形；检查构建和公理输出 | 逐条给出通过、退回或阻塞的结论和理由；退回修改后须重新验收 |

三个环节都有记录、且独立验收通过后，总调度才把相应证明标为完成，并在控制文件里下达合并指令。

### 自动接力的实际执行

1. **总调度起始核查并写工单**：核对论文公式、现有 Lean 生产者、量词与尺度、边界和非退化性，确定精确目标和互不冲突的文件范围。把工单规格写成 `docs/tickets/T####.md`（格式见 §7），并在 `docs/TASKS.md` 登记。难度较高的首轮任务标 `prover-hard`（推理强度 xhigh）。
2. **执行中枢领取并启动**：发现新工单后，写 `docs/queue/T####.state = claimed`，为该组启动一条 Workflow：
   - 阶段一：用 `prover` 或 `prover-hard` 子代理，在独立工作树里预审并证明；
   - 阶段二：阶段一报告预审 PASS 且模块构建成功后，才启动 `auditor` 子代理验收。
   执行中枢只转述工单内容，不增减要求。
3. **证明放行验收**：`prover` 完成指定模块构建，打印公理，写报告 `docs/reports/T####-prove.md`，在本组分支提交本单文件。`auditor` 检出该分支，核对预审 PASS、Lean 陈述、依赖、非退化见证、构建和公理，写报告 `docs/reports/T####-audit.md`。
4. **合并**：总调度读完两份报告、确认验收通过后，在 `docs/queue/CONTROL.md` 写合并指令。执行中枢只把本单文件并入主线，跑全库构建，写回结果。
5. **异常停止**：任何前项 FAIL／BLOCKED、已核对的产物发生变化或文件所有权冲突，执行中枢都停止下游阶段，写 `state = blocked` 和原因，由总调度重新核查。等待中的任务不能自行放宽条件。

**验收退回的分流**：低级模型的交付被验收判为 FAIL 时，总调度写一张修复工单，指定 `repairer`（高级模型）子代理接手，文件所有权随之转交；不把返工交回原来的低级模型。每次修复后，由没有参与这次修复书写的新 `auditor` 重新验收。BLOCKED 交总调度核查缺口，不按普通返工处理。

### 数学预审持续受阻时

1. **定位困难节点**：比较失败记录和依赖关系，找出真正阻塞后续证明的数学命题。写清它的精确陈述、已知输入、尝试过的路线和具体失败原因。
2. **启动强力论证**：总调度在 Cowork 里调用 1–3 名最高级模型子代理，给它们同一份精确问题和必要材料。它们可以通过本机访问只读地查看仓库，可以分别走不同路线，也可以互相检查关键步骤。
3. **数学交付物**：完整、明确、可核查的论证，包括精确的假设与结论、逐步推导、所用定理及其适用条件、边界情形，以及与相邻节点的连接。命题不成立或仍缺输入时，必须给出可核查的反例或准确的缺口，不能把猜想写成已证结论。
4. **复核并重新派单**：总调度核对交付物和各 agent 的分歧，把成立的论证拆成可以独立验收、文件互不冲突的工单，再走「预审并证明 → 独立验收」流程。未解决的缺口保留为阻塞。

## 3. 模型使用原则

项目启动时由用户指定低级、高级、最高级三档各对应哪个 Claude 模型。**模型级别**与**推理强度**是两项独立的设置。

| 级别 | 用途 | 示例（以你账户实际可用的为准） |
| --- | --- | --- |
| **高级** | 总调度、独立数学监督、所有独立验收、低级模型验收 FAIL 后的返工 | Opus；监督用 xhigh 或 max |
| **低级** | 所有首轮「数学预审并证明」 | Sonnet；按难度用 high 或 xhigh |
| **最高级** | 预审持续受阻或监督要求自检时的 1–3 名强力论证 agent | Fable 或当时最强的模型；推理强度 max |

与 ChatGPT 版的推理强度对应：High → high，Extra High → xhigh，Ultra → max。

**在哪里设置：**
- **Claude Code 子代理**：写在 `.claude/agents/*.md` 的 frontmatter 里（附录 A）。执行中枢只能按角色名调用，不能临时换模型。
- **总调度**：用户在 Cowork 里选定模型。
- **监督**：在定时任务的设置里指定模型。
- **强力论证 agent**：总调度调用时指定为最高级。

每张工单记录实际使用的模型、推理强度，以及每条证明的首次验收结果，供质量回顾。

### 复杂工单先拆分

有难度或范围大的目标，先沿证明依赖剥离出**简单、边界清楚、可以独立陈述和验收**的引理，用 `prover`（high）处理。剩下的关键障碍仍交给低级模型首轮处理，但用 `prover-hard`（xhigh）。下游工单须等上游成果通过独立验收，才能把它当作已证明的输入。不得为凑工单制造空真陈述、平凡改写或重复证明。

**拆单的前提：** 只拆已经有完整纸面论证的部分。一个 gate 的纸面证明还不存在时，先由总调度或强力论证 agent 写出它，不能先拆单、再边做边找证明。

### 派单的要求

工单规格必须写清：
- 每条目标 Lean 声明及其数学来源（公式编号、页码）；
- 预审须核对的关键步骤和边界情形；
- 可用的引理，以及依赖的已验收结果；
- 唯一可写文件和禁止改动的文件，根导入由谁负责；
- 必须完成的模块构建、全库构建和公理检查；
- 逐条的验收标准，以及选 high 还是 xhigh 的理由；
- 本单需要读的规则章节、报告和证据。不把整份历史文件列为必读。

**写出规格之前，总调度要亲自逐条核对**：所引用声明的签名、各假设的量词和作用域、每个加性误差项走到最终归一化之后的大小，以及各前提能否同时满足。核对不了的部分，在规格里写成「第 0 步只读核对，不成立则编译出否定结论并停下」。

**不得为方便拆分，擅自加上比论文论证和最终目标实际需要更强的要求。** 确需改变论文的假设或结论时，按 §4 交用户决定。

## 4. 开工前确认论文忠实度

如果项目依据一篇数学论文，总调度先与用户确认以下两项之一：

1. **严格按论文原文**：目标陈述须与指定版本一致；发现疑似错误时，先报告，等用户决定。
2. **允许微小改动**：明显笔误、必要条件或等价表述可以做最小修正，每处都记录原文、修改、理由和影响。涉及实质性数学变化时，仍由用户决定。

**路线级决定也要上报用户**，并在开工前给出工作量估计。例如「用真正的随机路径，还是只用单时刻分布」「用论文原证明，还是换一条替代论证」。一旦选错，后果是数百张工单。

确认结果写入 `docs/DECISIONS.md`，作为预审和验收的共同标准，不能由单个书写 agent 临时改变。

## 5. 目录、信箱与 GitHub

用户搭建本地文件夹和 GitHub 仓库，并在 Cowork 里把该文件夹连接给本任务。建议的目录如下（名称可调整）：

```text
project-name/
├── README.md
├── AGENTS.md                  # 所有 agent 共用的工作规则
├── CLAUDE.md                  # Claude Code 读取的规则入口（可指向 AGENTS.md）
├── .claude/agents/            # 角色定义：prover / prover-hard / auditor / repairer（附录 A）
├── lakefile.toml
├── ProjectName/               # Lean 源码，按模块划分文件所有权
├── docs/
│   ├── TASKS.md               # 活跃工单及负责人          —— 总调度独占
│   ├── STATUS.md              # 当前进度与阻塞            —— 总调度独占
│   ├── DECISIONS.md           # 用户确认的口径与裁定      —— 总调度独占
│   ├── ROUTES.md              # 路线账本：gate、路线、已用单数、闭合与否 —— 总调度独占
│   ├── HANDOFF.md             # 调度会话更替的交接包      —— 总调度独占
│   ├── tickets/T####.md       # 工单规格；写后不改，更正另开 T####-amend-N.md —— 总调度
│   ├── queue/
│   │   ├── CONTROL.md         # RUN / HOLD / AUDIT_FIRST、合并指令 —— 总调度独占
│   │   └── T####.state        # claimed / proving / auditing / done / fail / blocked —— 执行中枢独占
│   ├── reports/               # T####-prove.md、T####-audit.md —— 各自的子代理
│   ├── supervisor/            # 监督结论 —— 监督独占
│   └── archive/               # 已完成工单与过期状态
└── paper/                     # 经用户授权保存的论文资料
```

**所有权规则**：每个文件只有一个写入者，见上面的注释。总调度不写 `queue/*.state`；执行中枢不写 `TASKS.md`、`CONTROL.md` 和工单规格。

**git 纪律**：
- 只有执行中枢和它启动的子代理在 Mac 上执行 git 写操作。
- Cowork 一侧（总调度、监督、强力论证 agent）只读，查 git 时一律用 `git --no-optional-locks`，避免在仓库里留下锁文件。
- 每个书写或修复工单用自己的分支和工作树，提交只含本单文件。
- 执行中枢按 `CONTROL.md` 的合并指令把已验收的成果并入主线。未验收的证明不能成为后续工单的输入。
- 不经用户许可不 push。

**工作树里的 Lean 构建**：新工作树没有编译产物，从头编译代价很大。执行中枢创建工作树后，用符号链接共用 `.lake/packages`（Mathlib 等依赖不会被重编），用 APFS 写时复制克隆（`cp -c -R`）复制 `.lake/build`，再只编译本单涉及的模块。不要用硬链接（`cp -al`）：Lake 会原地改写 .olean，硬链接会把改动带回主工作区的缓存。

**常读文件定期精简**：总调度每 2 小时，以及每次交接前，检查 `TASKS.md`、`STATUS.md`、`DECISIONS.md`、`HANDOFF.md`、`AGENTS.md`、`CLAUDE.md`：
- 已完成的工单移入 `archive/`，完整过程留在 `reports/`；
- `STATUS.md` 只留当前进度、有效裁定、真实阻塞和下一步；
- 规则文件保持为简短的现行规则加阅读导航。

精简不得删除仍适用的数学或 Lean 约束。修改了生效中的规则，要记录生效时间，并在 `CONTROL.md` 里提示执行中枢。

## 6. 沟通、心跳与交接

- **执行与监督专注职责**：子代理和 Workflow 只交回结论，详细过程写进报告；执行中枢和监督都不与用户对话。需要用户裁定的事项统一由总调度提出。
- **总调度心跳**：Cowork 主会话用定时提醒回到本会话，间隔不超过 20 分钟。每次心跳先只看 `queue/HUB.alive`、`queue/*.state`、`reports/` 和 `supervisor/` 的修改时间：**与上次相比没有变化，就只排好下一次心跳然后结束本轮**，不读其他文件、不写汇报；有变化才读具体内容并处理。遇到 §1 列出的监督触发事件，立即手动触发监督并附上事件说明，同时更新 `docs/ROUTES.md`。**先排下一次心跳，再做本次的工作**，免得上下文压缩把它挤掉。
- **执行中枢轮询**：Claude Code 里用固定间隔的 `/loop 10m`（固定间隔在恢复会话后会继续）。没有新事时，只更新在线信号，不输出任何文字。状态全在文件里，会话被压缩或重启都不影响。
- **调度会话更替**：Cowork 会自动压缩上下文，但压缩会丢细节。总调度觉得上下文难以可靠维护时，主动把交接包写进 `docs/HANDOFF.md`，由用户在 Cowork 新开任务接管。
  - 会话依次命名为 `<项目名>调度 V1`、`V2` ……
  - 交接包至少包含：当前目标和用户已定的规则、模型映射与推理强度、活跃工单及负责人、文件所有权、已验收结果、未解决的数学节点、正在运行的 Workflow、新会话应立即处理的事项。
  - 新会话核对实际文件后，成为唯一的总调度；旧会话不再写 `CONTROL.md`。

## 7. 工单规格模板（`docs/tickets/T####.md`）

```text
工单编号：
工作组编号与任务类型：预审并证明／独立验收／修复
角色与模型：prover｜prover-hard｜auditor｜repairer（模型与推理强度由角色定义决定）
放行条件：阶段二开始前必须满足的条件（预审 PASS、模块构建成功、需核对的报告）
数学来源与目标：逐条列出本单包含的证明（公式编号、页码、目标 Lean 声明）
第 0 步只读核对：总调度未能亲自核实的点；不成立时编译出否定结论并停下
拆分关系：上游输入（须已验收）、下游目标、选 high 还是 xhigh 的理由
文件所有权：唯一可写文件、依赖文件、禁止改动的范围
根导入：是否由本组负责，具体文件
分支与工作树：本单分支名；合并目标
必读材料：本单相关的规则章节、报告、证据（不列整份历史文件）
验收标准：逐条
—— 以下由执行中枢和子代理填写到 state 文件与报告中 ——
数学预审：逐条 PASS／FAIL／BLOCKED 及依据
证明书写：构建结果、公理输出、报告位置
独立验收：逐条首次结论、验收者模型、退回原因及复验结果
返工转交：修复工单号、所有权转交、再次验收结果
最终状态：等待上游／预审中／书写中／待验收／验收中／退回／完成／阻塞
```

## 8. 附加规则：来自上一个项目的教训

1. **路线预算关卡**：同一路线累计约 50 张证明单仍没闭合一个 gate，必须暂停并做数学评审（§1 监督）。
2. **先有纸面证明，再拆单**（§3）。
3. **写规格前逐条核对接口**（§3）：签名、量词、每个加性项走到最终归一化之后的大小、各假设能否同时满足。
4. **按定义就满足的见证，也要估一下典型大小**：比如用全局最大值当见证，逻辑上成立，但数值上可能大到让下游的前提永远不成立。
5. **docstring 和蓝图不是证据**：「已证」以声明签名的假设为准。条件定理不能算作论文结论。
6. **Cowork 一侧永远不执行 git 写操作**（§5），会话重连后尤其要注意：删除权限会被重置，残留的锁文件会卡住执行端的提交。
7. **监督只管路线层面，按事件触发**：逐单核对交给预审和验收；监督不按固定钟点通读全部材料，否则开销可达项目总量的两到四成。

## 附录 A：`.claude/agents/` 角色定义草稿

字段名以你本机 Claude Code 版本的文档为准（特别是推理强度字段）。`tools` 限定角色可用的工具。

```markdown
<!-- .claude/agents/prover.md -->
---
name: prover
description: 首轮「数学预审并证明」。先写预审 PASS 记录，再在工单指定文件中写 Lean。
model: <低级模型>
effort: high
tools: Read, Grep, Glob, Edit, Write, Bash
---
你只执行一张工单。先读工单规格与其列出的必读材料。
1. 数学预审：逐条核对陈述、假设、量词、依赖、边界与可满足性，写入报告；未 PASS 不得写 Lean。
2. PASS 后只改「唯一可写文件」；编译指定模块；打印公理；在本单分支提交本单文件。
3. FAIL/BLOCKED：停止，报告精确缺口。不得新增假设、改目标陈述或扩大文件范围。

```

`prover-hard.md` 与 `prover.md` 相同，只把 `effort` 改为 `xhigh`。

```markdown
<!-- .claude/agents/auditor.md -->
---
name: auditor
description: 独立验收。只读审查，检出证明分支，在自己的工作树构建。
model: <高级模型>
effort: high
tools: Read, Grep, Glob, Bash
---
你没有参与本单的书写。逐条核对：Lean 陈述与数学目标是否一致；有无空真陈述、隐藏假设、
循环依赖；边界情形；非退化见证；模块和全库构建；公理只含 propext、Classical.choice、Quot.sound。
不修改任何源文件。结论逐条写 PASS／退回（附原因）／BLOCKED 到 docs/reports/T####-audit.md，
最后只回一行：工单号、结论、报告位置。
```

`repairer.md`：内容同 `prover.md`，模型改为高级。用于低级模型的交付被验收判 FAIL 之后的返工。

## 附录 B：执行中枢的启动提示词草稿

```text
你是本项目的执行中枢，只执行、不做决定。每轮：
```

## 附录 C：启用前用户要做的事

1. 指定低级、高级、最高级三档各对应哪个模型，以及总调度和监督用哪档。
2. 建好本地文件夹和 GitHub 仓库；在 Cowork 里把文件夹连接给调度任务。

5. 在 Cowork 里建监督定时任务：计划为每天一次兜底，使用本机，建议设为自动批准，只读。事件发生时由总调度手动触发（§1）。
6. 确认论文忠实度口径（§4），写入 `docs/DECISIONS.md`。
