# T632 — blocked: `flowXiL` is not upstream of `Hierarchy.Step3`

## Verdict

The requested Core-B extraction cannot satisfy all of its stated constraints.  The obstruction is
an undeclared dependency omitted by T626: the requested verbatim body of
`RBM.Step3.flowXiL` is

```lean
fun n N u ω => X.xiL E N u ω n
```

but `RBM.Sample.xiL` is itself declared later in `RBM1D/Hierarchy/Step3.lean` (currently lines
810–813).  It is not provided by either allowed direct import,
`RBM1D.Flow.Hypotheses` or `RBM1D.Flow.Scales`, and there is no other declaration of that name in
the repository.  Consequently `FlowFamiliesCore` cannot contain the verbatim `flowXiL` declaration
and compile before `Hierarchy.Step3`, while `Hierarchy.Step3` cannot import the core without a
cycle.

## Prototype check

I tested the only in-scope workaround that retains exactly the two prescribed imports: unfold
`Sample.xiL`, `loopXi`, and `loopMax` into the body of `flowXiL`.  Both proposed core modules then
built successfully, but the compatibility facade failed to build because existing Step-3 proofs
use the definitional body `flowXiL = Sample.xiL` directly:

```text
lake build RBM1D.Defs.StochDomMono       — success (2063 jobs)
lake build RBM1D.Flow.FlowFamiliesCore   — success (3460 jobs)
lake build RBM1D.Hierarchy.Step3         — failure
```

The failures occurred in `flow_xiL_le_of` (the proof unfolds `flowXiL` and uses
`Sample.xiL_le_add`) and `flow_sharpLoop_of` (the proof simplifies with
`[flowXiL, Sample.xiL, loopXi]`).  Repairing those proofs would violate the instruction that
`Hierarchy.Step3` remove only duplicate bodies, and the extracted `flowXiL` body would no longer be
verbatim.  All prototype edits were reverted; the only remaining T632 change is this report.

## Smallest consistent repair choices

1. Expand Core B to move `RBM.Sample.xiL` verbatim as an additional declaration and add the direct
   import `RBM1D.Loop.Split`; then the requested `flowXiL` body and existing facade proofs remain
   verbatim.  This requires deleting the old `Sample.xiL` body from `Hierarchy.Step3`.
2. Keep exactly the two prescribed imports, permit a definitionally equivalent unfolded body for
   `flowXiL`, and permit the two small compatibility-proof adjustments in `Hierarchy.Step3`.

Either choice changes an explicit T632 constraint, so implementation needs a routing decision.
No mathematical claim, hypothesis, paper delta, or downstream closure was introduced.
